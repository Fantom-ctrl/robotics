# Отчет о воспроизведении проблемы

## Ожидаемое поведение
Я запустила симулятор `turtlesim` вместе с нодой `patrol`. По задумке, черепаха должна была начать движение, так как моя нода генерирует и отправляет команды скорости (`linear.x=0.5`, `angular.z=0.3`).

## Фактический результат
Черепаха осталась неподвижной. Проверив топики, я выяснила следующее:
- `patrol` отдает сообщения в `/cmd_vel` (1 издатель, 0 подписчиков);
- `turtlesim` ожидает данные в `/turtle1/cmd_vel` (0 издателей, 1 подписчик).

Из-за несовпадения названий канал связи не создался, и управляющие сигналы до симулятора просто не дошли.

## Корень проблемы
Ошибка возникла в коде, где я инициализировала издатель с относительным именем:
```python
self.cmd_pub = self.create_publisher(Twist, 'cmd_vel', 10)
```
В то время как `turtlesim` ожидает команды в абсолютном топике `/turtle1/cmd_vel`. Из-за этой разницы граф ROS не смог связать узлы между собой.

## Примененное решение
Чтобы исправить ситуацию, я использовала перенаправление (remap) прямо при запуске:
```bash
ros2 run patrol patrol --ros-args -r cmd_vel:=/turtle1/cmd_vel
```
После этого связь установилась, и черепаха поехала. Частота публикации команд составляет около 10 Hz.

## Назначение базовых функций
Кратко опишу роль ключевых элементов в моем скрипте:
- `rclpy.init()` — инициализирует ROS и регистрирует ноду в общем графе.
- `rclpy.spin()` — запускает цикл обработки событий, в котором вызываются нужные функции.
- `callback` — функция-обработчик, срабатывающая по таймеру или при получении новых данных.
- `Ctrl+C` — сигнал остановки. Я перехватываю `KeyboardInterrupt`, чтобы нода завершила работу без ошибок.

## Нюансы завершения работы
При нажатии `Ctrl+C` моя нода `patrol` выключается моментально. Однако `turtlesim` продолжает работать еще некоторое время, и черепаха движется по инерции. Это штатное поведение, нужно просто подождать пару секунд, пока симулятор полностью остановится.
